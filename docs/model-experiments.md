# Model experiments

How the detectors in v0.2 were chosen: what was compared, how it was measured, what won, and
what the numbers do not tell you.

## TL;DR

| | v0.1 | v0.2 | how |
|---|---:|---:|---|
| heuristic (default, no model) | 93.60 % | **98.21 %** | R/synthetic classes, inner names, Play Services `za*/zz*`, known members, CV-tuned thresholds |
| ML (`--model`, default `lr`) | 98.90 % | **99.26 %** | 25 shape features, char 1–4-grams, C=16 |
| ML (`--algorithm lightgbm`) | – | **99.34 %** | same features, LightGBM |
| upstream architecture (word LSTM) | – | 92.96 % ± 6.25 | re-implemented in PyTorch for comparison |

Grouped, stratified 5-fold CV over the upstream dataset (see below). On a real R8 release APK,
the ML detector also gains a package rule. Without it, ML coverage was about 5 pt too low
(see [Real APK check](#real-apk-check)).

## Setup

- **Data**: `new_train.csv` from
  [liansecurityOS/apk-obfucation-detection](https://github.com/liansecurityOS/apk-obfucation-detection).
  It has 14,619 labelled classes, 5,260 of them obfuscated (36 %). Each row is a simple class name
  plus its method and field names. There are no package names.
- **Duplicates**: only 11,884 texts are unique. `R`, `a a`, `b a`, … recur across apps, and 4,111
  rows share their text with another row. 20 texts carry both labels.
- **Protocol**: `StratifiedGroupKFold(n_splits=5, shuffle=True, random_state=0)`, with groups
  formed by identical text, so a duplicate never sits on both sides of a split. Every model,
  including the neural ones, uses the same folds. The tables report the mean over folds and its
  standard deviation (±).
- **Tuning**: the heuristic's two thresholds are chosen per fold, on that fold's training part
  only. Model hyper-parameters were swept lightly (C ∈ {1, 4, 16}). The winner of that sweep is
  slightly optimistic.
- **Hardware**: Apple Silicon laptop, 12 cores. Neural models trained on MPS. Timings are
  per fold (≈11.7k training rows). µs/class is batch inference time.

v0.1's README quoted 98.9 % from an ungrouped random split. Grouping removes the duplicate leak,
but for that model the effect is small: 98.99 % ungrouped versus 98.90 % grouped.

### Candidates

- **shape-v1** (v0.1) has 5 features: whether the class name looks obfuscated, name length,
  obfuscated-member ratio, mean member length, and member count.
- **shape-v2** has 25 features. On top of v1 it adds: last name part (inner class), all parts
  obfuscated, `R`/`BuildConfig`, synthetic helpers, separate method and field counts and ratios,
  the ratio over non-framework members, length-1 and length-≤3 ratios, camelCase, digits,
  underscores, capitalised names, `za/zb/zz` prefixes, max length, and the heuristic-v2 verdict.
- **char / tagged**: TF-IDF over character n-grams within tokens (`char_wb`). "Tagged" prefixes
  each token with C/M/F (class/method/field).
- **upstream-lstm** is the upstream architecture: lower-cased word tokens,
  Embedding(100k, 100) → LSTM(128) → sigmoid, maxlen 256 with pre-padding, Adam, up to 24 epochs,
  and early stopping on validation accuracy with patience 5.
- **char-bilstm**: char Embedding(32) → BiLSTM(64) → max-pool. **char-cnn**: char Embedding(32)
  → Conv1d k=3/5/7 × 128 → max-pool → dropout 0.3.

## Findings

1. **Better features beat bigger models.** Switching shape-v1 to shape-v2 adds 0.3 pt to logistic
   regression. Gradient boosting on shape-v2 alone (no text at all, 321 KB) matches LR with
   n-grams. The models differ mainly in the features they get.
2. **The top models are within noise of each other.** LightGBM (99.34) is 0.08 pt over LR C=16
   (99.26). That is about 12 of 14,619 rows, and the fold-to-fold standard deviation is 0.06–0.08.
   Ensembling does not help.
3. **The upstream word-level LSTM is unstable on unseen identifiers.** Per-fold accuracy was
   97.1 / 98.7 / 86.8 / 98.2 / 84.0 %. Word tokens that appear only in the test fold map to
   "unknown", and grouping makes that the normal case. Character-level networks do not have
   this problem: the CNN reaches 98.85 ± 0.13. They still trail the linear models, though, and
   need PyTorch at inference time.
4. **The heuristic gained 4.6 pt from five rules.** Each rule targets an error class seen in the
   v0.1 misclassifications:
   - `R`, `R$drawable`, `BuildConfig`: short by convention, not by obfuscation.
   - `Foo$$ExternalSyntheticLambda0` with member `m`: judge by the outer class only.
   - `StaggeredGridLayoutManager$c`: an obfuscated inner class.
   - Play Services `zza`, `zae`, `zzcpr`.
   - Members such as `run`, `toString`, `writeToParcel`, `CREATOR`: R8 must keep these names, so
     they are excluded from the member ratio.

   All five folds picked the same thresholds (member ratio ≥ 0.4, at least 1 member). One
   consequence: a class whose only member is a one- or two-letter name (`Point { int x; }`)
   counts as obfuscated.
5. **The labels are noisy.** Many remaining ML "errors" are labelled 1 but are fully readable, for
   example `RotationGestureDetector calculateAngleBetweenLines …`. Others are partly obfuscated
   classes whose label could go either way. 20 texts appear with both labels. Above roughly 99 %,
   gains on this dataset may reflect fitting to label noise.

## Real APK check

Dataset accuracy is not the whole story, because the dataset has no packages and almost no
member-less classes. Real R8 output is full of both, for example interfaces repackaged to `d4.d`.

On Fossify Calculator 1.4.0 (release APK, 4,920 in-scope classes, no ground truth), detector
coverage was:

| detector | coverage |
|---|---:|
| heuristic v1 | 89.5 % |
| heuristic v2 | 89.9 % |
| ML lr, without package rule | 85.2 % |
| ML lightgbm, without package rule | 84.0 % |
| **ML lr, with package rule** | **90.0 %** |
| **ML lightgbm, with package rule** | **90.1 %** |

Heuristic v2 and ML lr disagreed on 244 classes. In 233 of them, ML called a class readable even
though both its package and its name looked renamed (`d4.d`, `H1.n`, `s5.r`), and 175 of those
have no members. v0.2 therefore ORs the model with a package rule: if every package segment and
the class name look like R8 output, the class counts as obfuscated. The CV numbers above are
unaffected, since the dataset has no packages. After the change the three detectors agree within
0.2 pt.

## Decisions for v0.2

- Default detector: heuristic v2. It needs no model, scores 98.2 %, and its rules are readable.
- `train` defaults to `lr` (LR C=16 + char 1–4 + shape-v2), which needs no extra dependency.
  `--algorithm lightgbm` is available for the last ~0.1 pt.
- The ML detector applies the package rule by default.
- The `train` hold-out is now grouped by identical text, like the CV above.

## Limitations

- Everything is measured on a single labelled dataset that we did not create. We could not audit
  its labelling rules, and its classes come from an unknown mix of apps and obfuscators.
- Groups are formed by identical text, not by app. Near-duplicates from the same library across
  apps (e.g. `MediaBrowserCompat$MediaItem`) can still land on both sides of a split.
- The real-APK check uses one app and has no ground truth. It shows agreement between detectors,
  not correctness.

## Next ideas

- **Ground truth from R8 mapping files.** A release build's `mapping.txt` says exactly which
  classes R8 renamed. Building open-source apps with and without minify would produce a large,
  correctly labelled dataset with packages, and would allow evaluating coverage per app instead
  of per class.
- **A `scan --mapping mapping.txt` mode** that reports exact coverage when the mapping file is
  available, falling back to detection when it is not.
